## When to Use

Use when the sequential optimizer (the `agent-optimizer` skill) has hit a local optimum (3 consecutive rejections) or when you want to explore the instruction space more broadly before committing to a direction.

## Prerequisites

- An existing optimization project (metadata.yaml, eval table with splits, build script)
- `scripts/build_agent_spec.py` in the workspace (generated by `agent-optimizer` setup — NOT bundled with this skill)
- At least one baseline eval recorded in optimization_log.md
- Python 3.11+ with PyYAML

## Configuration

GEPA uses defaults unless overridden by the user:

| Parameter | Default | Range | Notes |
|-----------|---------|-------|-------|
| population_size | 6 | 4-12 | Candidates per generation |
| max_generations | 10 | 3-20 | Hard stop ceiling |
| mini_batch_pct | 0.30 | 0.20-0.50 | Fraction of DEV questions per gen |
| convergence_threshold | 3 | 2-5 | Generations without improvement before stop |

Mini-batch evals use **1 run per candidate** (noise is inherent to small batches — accept it). Full `runs_per_split` from metadata.yaml applies only in Phase 4 validation.

## Execution Mode

Follows the toolkit-wide mode contract (`../../references/gate-inventory.md`) inherited from
the router — do not re-prompt for mode if it was already set there.

- **INTERACTIVE** (default if mode can't be determined): The Step 4 population-review gate
  and the Phase 4 winner-promotion gate are active. The user reviews and approves before
  proceeding.
- **AUTONOMOUS**:
  1. Step 4 (`GEPA-POPULATION-REVIEW`) — log the operator distribution table and proceed.
  2. Step 6's disposable `_GEPA_CAND_<N>` deployments (`AGENT-CANDIDATE-DEPLOY`) always
     auto-deploy in both modes — they are throwaway candidates, not production, so this was
     never a real gate.
  3. Phase 4 winner promotion (`GEPA-PROD-OVERWRITE`): **this is a permanent OPERATOR_REQUIRED
     gate per the gate inventory — it does NOT auto-resolve in AUTONOMOUS mode.** Present the
     validated diff and wait for an explicit accept/reject decision exactly as in INTERACTIVE.
     The only thing AUTONOMOUS changes here is that `GEPA-WINNER-SNAPSHOT` always fires
     automatically before any production write, in both modes, and the deterministic TSA/TEA
     floor check (Step 14, `AGENT-FLOOR-REJECT`) is applied with no exceptions — a winner
     below the floor is auto-rejected before the operator is even asked.
  Log every auto-resolution: `[AUTO-RESOLVED: <gate-id> → <default>]`. Convergence stops
  (Step 11) are algorithmic in both modes — they are not judgment gates and never require
  operator input.

Default to INTERACTIVE if the mode is unclear. If the user has stated a standing
"run to completion" / "don't stop until done" directive for this task, treat that as an
explicit request for AUTONOMOUS mode without asking again.

## Phase 1: Initialize Population

### Step 1: Read Context

Read `metadata.yaml` for all parameters. Read `optimization_log.md` — understand current scores and consecutive-rejection count. Read `DEPLOYMENT_INSTRUCTIONS.md` if present.

### Step 2: Resume or Initialize

Check if `gepa_state.json` exists in `<WORKSPACE_ROOT>/<AGENT_DIR>/`:
- **If exists:** Load state. Follow the Resume Protocol (end of this doc).
- **If not exists:** Initialize:
  ```bash
  python scripts/population_state.py init <WORKSPACE_ROOT>/<AGENT_DIR> \
    --pop-size 6 --agent-name <AGENT_NAME> \
    --baseline-fitness <last_accepted_combined_mean>
  ```

Generate a `run_id` (UUID) and store in `gepa_state.json`. Create log tables and
open the run record. Load `../../references/pattern-mining.md` for the full DDL.

```sql
CREATE TABLE IF NOT EXISTS <DATABASE>.<SCHEMA>.<AGENT_NAME>_OPT_RUNS ( ... );
CREATE TABLE IF NOT EXISTS <DATABASE>.<SCHEMA>.<AGENT_NAME>_OPT_CANDIDATES ( ... );
CREATE TABLE IF NOT EXISTS <DATABASE>.<SCHEMA>.<AGENT_NAME>_QUESTION_MANIFEST ( ... );
-- Use DDL from pattern-mining.md and references/question-manifest.md

INSERT INTO <DATABASE>.<SCHEMA>.<AGENT_NAME>_OPT_RUNS
    (run_id, optimizer_type, agent_fqn, sv_fqn, baseline_score, status, started_at)
VALUES ('<run_id>', 'GEPA', '<DATABASE>.<SCHEMA>.<AGENT_NAME>', '<SV_FQN>',
        <baseline_fitness>, 'IN_PROGRESS', CURRENT_TIMESTAMP());
```

Also create the shared cross-agent table if `opt_history_fqn` is set in `metadata.yaml`:
```sql
CREATE TABLE IF NOT EXISTS <META_DB>.<META_SCHEMA>.OPT_QUESTION_HISTORY ( ... );
```

### Step 3: Create Population

Load `references/mutation-operators.md` for the operator catalog, weights, and LLM prompt templates.

Create `gepa_population/` directory under `<WORKSPACE_ROOT>/<AGENT_DIR>/`.

For each candidate (1 to pop_size):

1. **Prepare candidate directory:**
   ```bash
   python scripts/mutate.py prepare \
     <WORKSPACE_ROOT>/<AGENT_DIR>/agent/ cand_<N> <WORKSPACE_ROOT>/<AGENT_DIR>
   ```

2. **Register candidate in state:**
   ```bash
   python scripts/population_state.py add-candidate \
     <WORKSPACE_ROOT>/<AGENT_DIR>/gepa_state.json \
     --id cand_<N> --generation 1 --mutations ""
   ```

3. **Select mutation operator:**
   ```bash
   python scripts/mutate.py select-operator --weights-file gepa_state.json
   ```
   Returns operator name + target file.

4. **Generate mutation (LLM-assisted):**
   ```bash
   python scripts/mutate.py get-prompt <operator> \
     gepa_population/cand_<N>/agent/
   ```
   This outputs a prompt. Use it to generate the mutation via Cortex Code (the agent itself applies the edit based on the prompt, failure context from optimization_log.md, and the operator's intent). Write the mutated content to the candidate's agent/ files.

   For the `add_retry_logic` operator (the only template-based operator): direct application without LLM is acceptable:
   ```bash
   python scripts/mutate.py apply-template add_retry_logic \
     gepa_population/cand_<N>/agent/
   ```

5. **Validate mutation (anti-pattern check):**
   ```bash
   python scripts/mutate.py validate \
     <WORKSPACE_ROOT>/<AGENT_DIR>/agent/ gepa_population/cand_<N>/agent/
   ```
   Rejects: verbose checklists, tool description changes, tool order changes, duplicate of prior rejected mutation.

### Step 4: Population Review (`GEPA-POPULATION-REVIEW`)

Present population matrix:

| Candidate | Operator | Target File | Mutation Summary |
|-----------|----------|-------------|-----------------|
| cand_1 | add_retry_logic | orchestration_instructions.md | Added 2x retry on transient errors |
| ... | ... | ... | ... |

Show diffs for each candidate.

**INTERACTIVE:** Wait for user approval before proceeding.
**AUTONOMOUS:** Log `[AUTO-RESOLVED: GEPA-POPULATION-REVIEW → proceeded]` and continue —
these are disposable candidates, not a production write.

## Phase 2: Evaluate Generation

### Step 5: Create Mini-Batch View

Load `references/mini-batch-strategy.md` for stratification rules and rotation constraints.

```bash
python scripts/sample_batch.py <DATABASE> <SCHEMA> <EVAL_TABLE> \
  <DEV_SPLIT_VALUE> --batch-pct 0.30 --generation <G> \
  --history-file <WORKSPACE_ROOT>/<AGENT_DIR>/gepa_state.json
```

Execute the returned SQL to create view `<DATABASE>.<SCHEMA>.GEPA_BATCH_GEN_<G>`.

### Step 6: Deploy Candidate Agents (`AGENT-CANDIDATE-DEPLOY`)

For each candidate, deploy without asking — these are disposable `_GEPA_CAND_<N>` agents,
not production, so no rollback clone applies (both modes):

> **Rollback gate:** Ask the user: "Want me to create a rollback clone first so we can undo this?" then execute on confirmation.

1. Build spec:
   ```bash
   python scripts/build_agent_spec.py --json \
     --agent-dir gepa_population/cand_<N>/agent/
   ```
2. Deploy:
   ```sql
   CREATE OR REPLACE AGENT <DATABASE>.<SCHEMA>.<AGENT_NAME>_GEPA_CAND_<N>
   FROM SPECIFICATION $$<spec_json>$$;
   ```

If resuming and agent already exists, skip creation.

### Step 7: Fire Evaluations

For each candidate, generate a YAML eval config pointing at `GEPA_BATCH_GEN_<G>` view with unique dataset name `<AGENT_NAME>_gepa_gen<G>_cand<N>_dev_ds`. Upload configs to stage.

Fire all simultaneously (1 run per candidate — no multi-run for mini-batch):
```sql
CALL EXECUTE_AI_EVALUATION('START',
  OBJECT_CONSTRUCT('run_name', 'gepa_gen<G>_cand<N>'),
  '<STAGE_PATH>/config_gepa_cand<N>.yaml');
```

Poll all in parallel using `references/eval-polling.md` pattern until every candidate reports `COMPLETED_METRICS > 0`.

### Step 8: Collect Scores

Query results per candidate:
```sql
SELECT METRIC_NAME, AVG(EVAL_AGG_SCORE) AS MEAN_SCORE
FROM TABLE(SNOWFLAKE.LOCAL.GET_AI_EVALUATION_DATA(
  '<DATABASE>', '<SCHEMA>', '<AGENT_NAME>_GEPA_CAND_<N>',
  'CORTEX AGENT', 'gepa_gen<G>_cand<N>'))
WHERE METRIC_NAME IS NOT NULL
GROUP BY METRIC_NAME;
```

**Log per-question scores** (mandatory — see `../../references/pattern-mining.md` for INSERT pattern):

```sql
-- Into per-agent manifest
INSERT INTO <DATABASE>.<SCHEMA>.<AGENT_NAME>_QUESTION_MANIFEST
    (INPUT_ID, INPUT_TEXT, METRIC_NAME, SCORE, SOURCE, OPTIMIZER_TYPE, RUN_ID,
     RUN_LABEL, VARIANT, ITERATION, AGENT_FQN, DURATION_MS, LLM_CALL_COUNT, ERROR)
SELECT INPUT_ID, INPUT, METRIC_NAME, EVAL_AGG_SCORE,
    'gepa_gen', 'GEPA', '<run_id>',
    'gepa_gen<G>_cand<N>', NULL, NULL,
    '<DATABASE>.<SCHEMA>.<AGENT_NAME>_GEPA_CAND_<N>',
    DURATION_MS, LLM_CALL_COUNT, ERROR
FROM TABLE(SNOWFLAKE.LOCAL.GET_AI_EVALUATION_DATA(
    '<DATABASE>', '<SCHEMA>', '<AGENT_NAME>_GEPA_CAND_<N>',
    'CORTEX AGENT', 'gepa_gen<G>_cand<N>'))
WHERE METRIC_NAME IS NOT NULL;

-- Into shared cross-agent history (if opt_history_fqn set in metadata.yaml)
INSERT INTO <META_DB>.<META_SCHEMA>.OPT_QUESTION_HISTORY
    (agent_fqn, sv_fqn, optimizer_type, run_id, generation, operator,
     input_id, input_text, metric_name, score, delta_vs_baseline,
     source, run_label, test_category)
SELECT
    '<DATABASE>.<SCHEMA>.<AGENT_NAME>', '<SV_FQN>', 'GEPA', '<run_id>',
    <G>, '<operator_for_cand_N>',
    INPUT_ID, INPUT, METRIC_NAME, EVAL_AGG_SCORE,
    EVAL_AGG_SCORE - <baseline_fitness>,
    'gepa_gen', 'gepa_gen<G>_cand<N>', TEST_CATEGORY
FROM TABLE(SNOWFLAKE.LOCAL.GET_AI_EVALUATION_DATA(
    '<DATABASE>', '<SCHEMA>', '<AGENT_NAME>_GEPA_CAND_<N>',
    'CORTEX AGENT', 'gepa_gen<G>_cand<N>'))
WHERE METRIC_NAME IS NOT NULL;
```

Repeat for each candidate in the generation.

## Phase 3: Select and Evolve

### Step 9: Run Tournament

Load `references/tournament-rules.md` for selection mechanics, elitism, and diversity rules.

```bash
python scripts/tournament.py <scores_json> \
  <WORKSPACE_ROOT>/<AGENT_DIR>/gepa_state.json
```

Returns: winners (top half), losers (bottom half), updated operator weights.

### Step 10: Update State

- Record generation results in `gepa_state.json` via `population_state.py`
- Update operator weights: winners' operators get +0.02, losers' get -0.01 (floor: 0.02)
- Increment `convergence_counter` if `best_fitness` unchanged, else reset to 0
- Remove eliminated candidates from state:
  ```bash
  python scripts/population_state.py remove-candidates <state_path> --ids <loser1>,<loser2>
  ```

**Log each candidate result:**

```sql
INSERT INTO <DATABASE>.<SCHEMA>.<AGENT_NAME>_OPT_CANDIDATES
    (candidate_id, run_id, generation, operator, target_file,
     mean_score, delta_vs_baseline, regression_count, accepted)
VALUES
    ('gepa_gen<G>_cand<N>', '<run_id>', <G>, '<operator>', '<target_file>',
     <mean_score>, <mean_score> - <baseline_fitness>, <regression_count>,
     <TRUE if winner else FALSE>);
-- Repeat for each candidate in the generation
```

### Step 11: Check Convergence

Load `references/convergence-criteria.md`. Evaluate stop conditions:

| Condition | Result |
|-----------|--------|
| convergence_counter >= threshold | CONVERGED |
| current_generation >= max_generations | CONVERGED |
| All candidates within 2% of each other | CONVERGED (population collapse) |
| No candidate beats baseline after 3 gens | FAILED |
| Gen 1 winner >10% above baseline | CONVERGED (early termination) |

**If NOT converged:**
- Drop loser agents: `DROP AGENT IF EXISTS <AGENT_NAME>_GEPA_CAND_<N>;`
- Drop generation view: `DROP VIEW IF EXISTS GEPA_BATCH_GEN_<G>;`
- Mutate winners to fill empty candidate slots (repeat Phase 1 Step 3 for new candidates only)
- Return to Phase 2

**If CONVERGED (success):** Advance winner to Phase 4.

**If FAILED:** Log failure to `optimization_log.md`, run Cleanup (end of doc), STOP.

## Phase 4: Validate Winner

### Step 12: Deploy Winner as Validation Candidate

Build the winner's spec and deploy it as a disposable candidate — **not** the primary
agent — so full evaluation below runs against a copy, not production:

```bash
python scripts/build_agent_spec.py --agent-dir gepa_population/<winner_cand>/agent/ --json \
  --output <WORKSPACE_ROOT>/<AGENT_DIR>/gepa_winner_spec.json
```
```sql
CREATE OR REPLACE AGENT <DATABASE>.<SCHEMA>.<AGENT_NAME>_GEPA_WINNER
FROM SPECIFICATION $$<gepa_winner_spec.json contents>$$;
```

### Step 13: Full Evaluation

Run FULL dev eval (all `<RUNS_PER_SPLIT>` runs) against `<AGENT_NAME>_GEPA_WINNER` — same
pattern as `agent-optimizer` optimize/SKILL.md Step 2. Run FULL test eval against the same
candidate — same as `agent-optimizer` optimize/SKILL.md Step 8. Production is untouched
throughout.

### Step 14: Accept/Reject

Hand off to `agent-optimizer` review/SKILL.md for the standard paired t-test accept/reject
decision, computed from the `<AGENT_NAME>_GEPA_WINNER` candidate's results vs. baseline.

> **⚠️ TSA/TEA floor check (`AGENT-FLOOR-REJECT`) — do this before accepting, not just the
> regression test.** GEPA's fitness function (see `references/tournament-rules.md`) selects
> on `answer_correctness` only. The standard paired t-test in review/SKILL.md rejects on
> *regression* (TSA/TEA getting worse), but will happily ACCEPT a winner whose TSA/TEA were
> already poor at baseline and never improved. Before accepting: compare the winner's
> `tool_selection_accuracy` and `tool_execution_accuracy` scores to the baseline. If either is
> below ~0.60, or is not meaningfully better than baseline despite multiple generations, this
> is an automatic reject in **both modes** — log `[AUTO-RESOLVED: AGENT-FLOOR-REJECT →
> rejected, TSA=<v>]` and skip straight to the REJECTED branch of Step 15 without presenting
> the promotion gate. (Recall: TSA/TEA v3 scores may be embedded in `EXPLANATION` text rather
> than the aggregate score field — see agent-evaluation/SKILL.md Phase 5.1 before reading
> these numbers.)

If the winner clears the floor and the t-test accepts it, proceed to the `GEPA-PROD-OVERWRITE`
promotion gate in Step 15 — **this is a permanent OPERATOR_REQUIRED gate; it does not
auto-resolve in AUTONOMOUS mode.** Present the validated DEV/TEST diff and wait for an
explicit accept/reject decision in both modes. Log the operator's decision:
`[OPERATOR-DECISION: GEPA-PROD-OVERWRITE → <accept/reject>]`.

### Step 15: Log and Cleanup

**If ACCEPTED (after the `GEPA-PROD-OVERWRITE` gate is explicitly accepted):**
- First snapshot the current production spec (rollback state, `GEPA-WINNER-SNAPSHOT` —
  `AUTO_REMEDIATE`, always fires with no prompt in either mode) to
  `snapshots/gepa_<DATE>_pre_apply/`.
- Only then copy winner's `agent/*.md` files to `<WORKSPACE_ROOT>/<AGENT_DIR>/agent/`
  (replacing current), build, and deploy to the primary agent:
  ```bash
  python scripts/build_agent_spec.py --agent-dir <WORKSPACE_ROOT>/<AGENT_DIR>/agent/
  <CLI_TOOL> sql --connection <CONNECTION> --filename deploy.sql
  ```
- Log to `optimization_log.md`: `## [GEPA gen <G>]` entry including:
  - Winner's mutation chain (operators applied across generations)
  - Per-generation best scores
  - Total eval calls consumed
- Snapshot winner to `snapshots/<iter_name>/`
- Counts as **1 accepted iteration** for `flag_sweep_baseline.json` revalidation interval

```sql
UPDATE <DATABASE>.<SCHEMA>.<AGENT_NAME>_OPT_RUNS
SET final_score = <winner_score>, delta = <winner_score> - baseline_score,
    winner_operator = '<dominant_operator>', generations_run = <G>,
    status = 'CONVERGED', ended_at = CURRENT_TIMESTAMP()
WHERE run_id = '<run_id>';
```

**If REJECTED (floor check failed, t-test rejected, or operator declined promotion):**
- Production was never touched — no revert needed.
- Log rejection with reason.

```sql
UPDATE <DATABASE>.<SCHEMA>.<AGENT_NAME>_OPT_RUNS
SET final_score = <winner_score>, delta = <winner_score> - baseline_score,
    generations_run = <G>, status = 'BUDGET_EXHAUSTED', ended_at = CURRENT_TIMESTAMP()
WHERE run_id = '<run_id>';
```

**Always (after accept or reject):**
- `DROP AGENT IF EXISTS <AGENT_NAME>_GEPA_WINNER;`
- `DROP AGENT IF EXISTS <AGENT_NAME>_GEPA_CAND_<N>;` for all candidates
- `DROP VIEW IF EXISTS <DATABASE>.<SCHEMA>.GEPA_BATCH_GEN_<G>;` for all generations
- Remove `gepa_population/` directory
- Remove `gepa_state.json`
- Remove GEPA eval configs from stage

## Resume Protocol

On Phase 1 Step 2, if `gepa_state.json` exists:

1. Read `current_generation` from state
2. Check if eval results exist for that generation:
   ```sql
   SELECT COUNT(*) FROM TABLE(SNOWFLAKE.LOCAL.GET_AI_EVALUATION_DATA(
     '<DATABASE>', '<SCHEMA>', '<AGENT_NAME>_GEPA_CAND_1',
     'CORTEX AGENT', 'gepa_gen<G>_cand1'))
   WHERE METRIC_NAME IS NOT NULL;
   ```
3. **Results found for all candidates** → Skip to Phase 3 Step 9 (tournament)
4. **No results but agents exist** (check `SHOW AGENTS LIKE '<AGENT_NAME>_GEPA_CAND_%'`) → Skip to Phase 2 Step 7 (re-fire evals)
5. **No agents but `gepa_population/` exists** → Skip to Phase 2 Step 6 (deploy from local)
6. **Nothing exists** → State is stale; delete `gepa_state.json` and start fresh

## Cleanup Intent

If user says "gepa cleanup" or "clean gepa agents":

1. Load `gepa_state.json` (if exists) → get candidate agent names and generation count
2. If no state file, probe: `SHOW AGENTS LIKE '<AGENT_NAME>_GEPA_CAND_%' IN SCHEMA <DATABASE>.<SCHEMA>;`
3. For each found agent: `DROP AGENT IF EXISTS <DATABASE>.<SCHEMA>.<agent_name>;`
4. For each generation view: `DROP VIEW IF EXISTS <DATABASE>.<SCHEMA>.GEPA_BATCH_GEN_<G>;`
5. Remove local artifacts: `gepa_population/`, `gepa_state.json`
6. Report what was cleaned
