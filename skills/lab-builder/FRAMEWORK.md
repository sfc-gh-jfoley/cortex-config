# Lab Framework

This document is the canonical design standard for all Snowflake hands-on labs in this workspace.
All new labs **must** follow this structure. Use `template/` (co-located in this skill directory) as the starting point.

---

## Customer Discovery: Before You Build Anything

**The SE's first job is a conversation, not a lab.**

Do not pick a lab from `LABS_INDEX.md` and provision it without talking to the company first.
A generic lab is a fallback. A tailored lab is what makes the session memorable.

### What to learn in the discovery call

| Question | What it drives |
|----------|----------------|
| "What problem are you trying to solve with Snowflake?" | The hero question |
| "Who will be in the room?" (DE / Analyst / Business User) | Module depth, prompt style, skip lists |
| "What's your data domain?" | Synthetic data domain (should feel like their world) |
| "What Snowflake features have you already used?" | What to skip, what to show as new |
| "What should participants be able to do after?" | Objectives and validate.sql checks |
| "How much time do we have?" | Duration tier (30 / 60–90 / 2hr) |
| "Individual databases per participant, or a shared Snowflake account with per-user schemas?" | **Company decides this — not the SE.** Their DBA or security policy owns the answer. Drives the entire grant model. |

### Output of discovery → input to lab-builder

Take the conversation notes and run `invoke skill lab-builder`. The Phase 1 intake
questions map 1:1 to what the company told you.

If an existing lab is close enough in domain and hero question, adapt it.
If not, build a new one — `lab-builder` takes ~30 minutes to scaffold a full lab.

### Domain tailoring rule

The synthetic data must feel like the company's world.

| If the company is... | Use this domain |
|---------------------|-----------------|
| Telecom (Verizon, AT&T) | Network devices, subscribers, CDRs, 5G signal metrics |
| Healthcare | Patient encounters, device readings, lab results, claims |
| Retail / Commerce | Orders, products, customers, transactions, returns |
| Media / Streaming | Titles, viewing sessions, recommendation events |
| Financial services | Accounts, transactions, risk signals, portfolios |
| Industrial / Manufacturing | Sensors, machines, maintenance logs, downtime alerts |

A Verizon lab should not use generic "DEVICES" with no telecom context.
It should use towers, node IDs, signal strength, subscriber throughput.

## Design Principles

1. **Self-contained** — no Snowhouse, Raven, or external account access required. Synthetic data is bundled in `hol_setup.sql`.
2. **Three paths** — every lab offers:
   - **(A) CoCo-guided** — structured CoCo prompts in `hol_prompts.md`, learner follows with Cortex Code CLI
   - **(B) Snowsight manual** — step-by-step SQL/UI instructions for browser-only environments
   - **(C) Easy path** — drop-in prompts that do the work automatically for time-constrained demos
3. **Completable in one sitting** — standard duration 60–90 min; short labs 30 min; deep labs max 2 hr
4. **Validation-gated** — `validate.sql` at the end; learner runs it, gets PASS/FAIL per objective
5. **Failure moments** — at least one exercise intentionally shows a limitation, then resolves it (Sony SPE before/after pattern)
6. **Teardown included** — `hol_teardown.sql` removes all objects; labs are safe for shared accounts

## Canonical Directory Structure

```
labs/<lab-slug>/
├── AGENTS.md                  # CoCo context — generated by lab-builder (read on session open)
├── README.md                  # Objectives, prerequisites, agenda table, duration, audience
├── modules/
│   ├── 00_setup.md            # Account prereqs, run hol_setup.sql, verify
│   ├── 01_<topic>.md          # Module 1 — numbered, named
│   ├── 02_<topic>.md          # Module 2
│   └── ...
├── hol_setup.sql              # DDL + synthetic data (CREATE + INSERT, idempotent)
├── validate.sql               # Completion checks — prints PASS/FAIL per objective
├── hol_teardown.sql           # DROP everything created in hol_setup.sql (pattern-specific)
├── hol_prompts.md             # Structured CoCo prompts — A-path exercises per module
├── hol_facilitator_guide.md   # SE delivery script and timing guide
└── facilitator_setup.sql      # Elevated setup (DBA/SE only) — if elevated grants needed
```

**Optional additions:**
- `examples/` — complete working reference SQL (not shown during lab)
- `hints/` — progressive hints per module (for self-paced formats)
- `solutions/` — full solutions (facilitator copy)

## validate.sql Pattern

```sql
-- Lab Completion Validator
-- Run this after completing all modules.
-- Each check prints PASS or FAIL.

SET schema_ref = '<DB>.<SCHEMA>';

SELECT
    'Objective 1: <description>'     AS check_name,
    CASE WHEN <condition> THEN 'PASS' ELSE 'FAIL' END AS status
UNION ALL
SELECT
    'Objective 2: <description>',
    CASE WHEN <condition> THEN 'PASS' ELSE 'FAIL' END
-- ... one row per objective
ORDER BY check_name;
```

## facilitator_setup.sql Pattern

Some labs require elevated privileges or long-running provisioning that cannot be done
in a participant's `hol_setup.sql`. These belong in a separate `facilitator_setup.sql`.

**Ownership model for customer workshops:**
- The **customer DBA** runs `facilitator_setup.sql` (they own the account, they own provisioning)
- The **account SE** verifies the DBA's work using `grant_audit.sql` before the workshop
- The SE does **not** run provisioning on customer accounts directly — they verify it

**Use `facilitator_setup.sql` for:**
- Compute pool creation (ML Jobs, Container Runtime, SPCS) — requires quota approval
- Creating roles and grants — the DBA-owned section
- Cortex Search service initial creation (takes 1-5 min, not suitable for live demo)
- Dynamic Table initial hydration (first refresh can take 2-10 min)
- Any `GRANT DATABASE ROLE SNOWFLAKE.* TO ROLE ...` (requires ACCOUNTADMIN)
- Creating participant users and assigning to HOL role (DBA task)

**Standard file header:**
```sql
-- ============================================================
-- Facilitator Setup: <Lab Name>
-- ── WHO RUNS THIS ──────────────────────────────────────────
-- Run by: Customer DBA (as SYSADMIN / ACCOUNTADMIN)
-- Verified by: Account SE using grant_audit.sql (after DBA completes)
-- Run BEFORE the workshop — not during.
-- Estimated time: ~N minutes
-- ── HAND-OFF ───────────────────────────────────────────────
-- After running: SE verifies every check in grant_audit.sql = ✓
-- Then: SE sends participants their credentials and pre-work doc
-- ============================================================
USE ROLE SYSADMIN;
```

**Participant `hol_setup.sql`** should only contain DDL a participant role can run —
CREATE TABLE, INSERT, CREATE SEMANTIC VIEW, CREATE STREAMLIT.

**FRAMEWORK.md rule:** Any lab with a `facilitator_setup.sql` must document it in
the README under a "Facilitator: Pre-Workshop Steps" section with a note that the
customer DBA runs setup and the SE verifies with `grant_audit.sql`.

## Duration Targets and Curriculum Planning

Time available is the primary constraint. Map it to sessions, modules, and skip lists
before building anything. The lab-builder skill does this in Phase 0.5 — the table
below is the reference it uses.

| Time available | Format | Sessions | Module count | Suggested structure |
|----------------|--------|----------|--------------|---------------------|
| 1 hour | Single session | 1 | 1–2 modules | Setup (10 min) + 1 feature module (40 min) + validate (10 min). Skip failure moment or compress it to a callout. |
| 90 minutes | Single session | 1 | 2–3 modules | Setup (15 min) + 2 modules (30 min each) + validate (15 min). Includes one failure moment. |
| Half day (3 hr) | Single session | 1 | 3–4 modules | Setup (20 min) + 3 modules (40 min each) + validate + wrap. Full failure moment. |
| Full day | Two 3-hr sessions | 2 | 5–6 modules | Session 1: setup + core feature + failure moment. Session 2: advanced patterns + capstone/build-out. Lunch break between. |
| Multi-day | Multiple sessions | 3+ | 6–8 modules | Day 1: foundation + core. Day 2: advanced + integration. Day 3: capstone project, teams present outputs. |

**Module time budget:**
- Setup module (Module 00): always 15–20 min (includes Pre-Work verification)
- Feature module: 25–45 min depending on complexity
- Failure moment adds 10–15 min to whichever module contains it
- Validate + wrap: 10–15 min at the end of each session

**Audience adjustments:**
- Business Users / Executives: cut module count by 1, add 10 min per module for context-setting
- Mixed audience (DE + Analyst): run two parallel tracks or skip DE-only SQL modules for Analysts
- SE internal training: full depth, include failure moment, add Q&A time after each module

**Sample lab as starting point:**

Before building from scratch, check the existing labs in `LABS_INDEX.md`. A tailored lab
often starts with an existing lab's structure and swaps the data domain rather than
rebuilding everything. The `cai/` lab is the gold standard reference for module pacing.

## Participant Isolation Pattern

**Decide this when building the lab — not on delivery day.** The isolation pattern
determines how participants are separated from each other, which grants the DBA must
create, and whether `hol_setup.sql` runs once (SE) or once per participant.

Document the choice in the README.md `**Isolation:**` field. It directly controls what
goes in `facilitator_setup.sql` (DBA runs) and `grant_audit.sql` (SE verifies).

---

### Pattern A: Schema-per-User (default — shared account)

Each participant creates their own schema inside a shared lab database.
Mirrors the `cai/` gold standard (`SET MY_SCHEMA = 'YOURNAME_HOL'`).

**When to use:**
- Workshop on a shared customer or internal Snowflake account
- Participants can see each other's schema names but not data (schema-scoped permissions)
- Most common pattern — works for all 4 current labs

**`hol_setup.sql` pattern:**
```sql
SET MY_DB     = 'LAB_DATABASE';
SET MY_SCHEMA = 'CHANGE_ME';    -- ← participant sets this (e.g. 'JFOLEY_HOL')

USE DATABASE IDENTIFIER($MY_DB);
CREATE SCHEMA IF NOT EXISTS IDENTIFIER($MY_SCHEMA);
USE SCHEMA IDENTIFIER($MY_SCHEMA);
```

**DBA grants required:**
```sql
-- Core (all labs)
GRANT USAGE ON DATABASE <LAB_DB> TO ROLE <HOL_ROLE>;
GRANT CREATE SCHEMA ON DATABASE <LAB_DB> TO ROLE <HOL_ROLE>;
GRANT USAGE ON WAREHOUSE <HOL_WH> TO ROLE <HOL_ROLE>;
-- Cortex labs only
GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE <HOL_ROLE>;
-- Streamlit labs only
-- (CREATE STREAMLIT granted at schema level after participant creates schema)
-- Dynamic Tables labs only
-- (CREATE DYNAMIC TABLE granted at schema level)
```

---

### Pattern B: Database-per-User (dedicated sandbox accounts)

Each participant gets their own pre-created database: `HOL_JFOLEY`, `HOL_SMITHJ`, etc.

**When to use:**
- Each participant has a dedicated sandbox account (common in large enterprise workshops)
- Lab requires full database ownership (e.g., dbt with separate catalogs)
- Customer security policy prevents cross-schema visibility even in same DB

**`hol_setup.sql` pattern:**
```sql
SET MY_DB = 'HOL_CHANGE_ME';    -- ← participant sets this (e.g. 'HOL_JFOLEY')

USE DATABASE IDENTIFIER($MY_DB);
CREATE SCHEMA IF NOT EXISTS LAB;
USE SCHEMA LAB;
```

**DBA grants required:**
```sql
-- DBA pre-creates one DB per participant, then:
GRANT OWNERSHIP ON DATABASE <HOL_USERNAME_DB> TO ROLE <HOL_ROLE> COPY CURRENT GRANTS;
GRANT USAGE ON WAREHOUSE <HOL_WH> TO ROLE <HOL_ROLE>;
GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE <HOL_ROLE>;
```

### Grant Requirements by Module Type

The DBA uses this table to build `facilitator_setup.sql`. The SE uses `grant_audit.sql`
to verify every row before the workshop.

| Module Feature | Additional Grant (beyond base DB+schema+warehouse) |
|----------------|-----------------------------------------------------|
| Base data access | USAGE ON DATABASE, CREATE SCHEMA (or OWNERSHIP on DB) |
| Cortex AI (any) | `GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE <HOL_ROLE>` |
| Streamlit in Snowflake | `GRANT CREATE STREAMLIT ON SCHEMA <db>.<schema> TO ROLE <HOL_ROLE>` |
| Dynamic Tables | `GRANT CREATE DYNAMIC TABLE ON SCHEMA <db>.<schema> TO ROLE <HOL_ROLE>` |
| Snowflake Notebooks | `GRANT CREATE NOTEBOOK ON SCHEMA <db>.<schema> TO ROLE <HOL_ROLE>` |
| dbt (write models) | `GRANT CREATE TABLE ON SCHEMA <db>.<schema> TO ROLE <HOL_ROLE>` |
| ML Jobs / SPCS | `CREATE COMPUTE POOL` — requires ACCOUNTADMIN + quota approval (facilitator_setup.sql only) |

**Key rule:** Schema-level grants (Streamlit, DT, Notebooks) can only be issued after
the schema exists. For Pattern A (schema-per-user), grant these after participants run
`hol_setup.sql`, or grant to a future schema via `GRANT ... ON FUTURE SCHEMAS IN DATABASE`.

**FUTURE SCHEMAS shortcut (Pattern A):**
```sql
-- DBA runs this once — covers all schemas participants will create:
GRANT CREATE STREAMLIT ON FUTURE SCHEMAS IN DATABASE <LAB_DB> TO ROLE <HOL_ROLE>;
GRANT CREATE DYNAMIC TABLE ON FUTURE SCHEMAS IN DATABASE <LAB_DB> TO ROLE <HOL_ROLE>;
GRANT CREATE NOTEBOOK ON FUTURE SCHEMAS IN DATABASE <LAB_DB> TO ROLE <HOL_ROLE>;
GRANT CREATE TABLE ON FUTURE SCHEMAS IN DATABASE <LAB_DB> TO ROLE <HOL_ROLE>;
```

### SE Verification: grant_audit.sql

After the DBA completes setup, the SE runs `grant_audit.sql` (template at
`labs/_template/grant_audit.sql`). Every row must show ✓ before sending
participants the pre-work doc.

## Canonical Pattern: Before/After Failure

Adapted from the Sony SPE lab pattern. The most memorable labs show:
1. A natural failure (fuzzy title match fails, query returns 0 rows, pipeline fails)
2. Diagnosis using available tools
3. Resolution (add Cortex Search, fix semantic view, add alert)
4. Re-run showing success

Always frame the failure as expected, not a mistake.

## CoCo Prompt Style (Path A)

Based on the Cox CCI pattern — the best model for CoCo-guided labs:

```
I'm working in Snowflake database [YOUR_DB], schema PUBLIC, warehouse COMPUTE_WH.
I have these tables: <list with brief description>.

<Specific ask — what to build/analyze/explain>
```

- Always include database + schema + warehouse upfront
- Always tell CoCo what tables exist and what they contain
- End with a specific, bounded ask
- Add `> **What to watch for:**` callout noting what CoCo should infer or demonstrate

## Relationship to Demo Framework

Labs and demos are distinct:

| Dimension | Lab | Demo |
|-----------|-----|------|
| Purpose | Teach a skill | Show a capability |
| Driver | Learner does the work | AI/CoCo does the work |
| Data | Synthetic, bundled | Customer-mirrored (Snowhouse/Snow Twin) |
| Duration | Fixed modules | Variable, account-specific |
| Framework | `labs/` | `ship_demo/` |
| Discovery | `LABS_INDEX.md` | `DEMOS_INDEX.md` |

Use demos to prepare for a customer meeting. Use labs for internal SE training, College of AI, or customer workshops.
